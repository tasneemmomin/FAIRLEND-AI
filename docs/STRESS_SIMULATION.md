# Financial Stress Early-Warning & Future Scenario Intelligence
## Technical Documentation & Experimental Evaluation Design

Module: `backend/services/financial_stress/` • API: `/api/stress/*` • Version: Calc v1.0.0

---

## 1. What This Feature Is (and Is Not)

| Is | Is **NOT** |
|---|---|
| A deterministic, versioned financial simulation engine | A statistically validated default-probability model |
| Assumption-based what-if exploration of affordability | A forecast of future income, expenses, or loan default |
| A loan approval/rejection decision-maker | A replacement for the policy engine, online model, or officer judgment |

All scenario results are computed from a fixed set of closed-form arithmetic rules
(see §2). The same inputs always produce the same outputs (unit-tested determinism).
Explanations are generated by templates using actual calculated values — no LLM
participates in any calculation path.

---

## 2. Core Calculations (Documented Rules — Calc v1.0.0)

All monetary values are INR.

```
DisposableIncome    = NetIncome − ExistingEMI − MonthlyExpenses
RemainingBalance    = NetIncome − ExistingEMI − MonthlyExpenses − ProposedEMI
TotalEMIBurden      = ExistingEMI + ProposedEMI          (expense burden kept separate)
ExpenseBurdenRatio  = MonthlyExpenses / NetIncome × 100  (never counted as EMI)
FOIR                = (ExistingEMI + ProposedEMI) / NetIncome × 100   [0 if income ≤ 0]
ProposedEMI         = P·r·(1+r)^n / ((1+r)^n − 1), r = rate/12/100  (safe zero-rate division)
```

Zero or missing income never divides by zero; such cases produce the
**"Insufficient Information"** indicator instead of a misleading value.

### Stress Indicator Bands (documented, admin-configurable)
| Remaining balance vs net income | Indicator |
|---|---|
| > 20% | Stable Under Assumptions |
| 10–20% | Reduced Financial Buffer |
| 0–10% | Elevated Financial Stress |
| ≤ 0 | Negative Monthly Balance |
| income missing/zero | Insufficient Information |

### FOIR Risk Bands (mirrors `config/policy_rules.yaml`)
≤ 35% safe · ≤ 45% moderate · ≤ 55% high · > 55% critical (60% = policy hard rule).

### Data-Provenance Labelling
Every input is tagged: `verified_intake` (customer-confirmed), `estimated_assumption`
(40% of income documented default when expenses not supplied), `computed_from_terms`
(EMI from loan amount/tenure/rate), `policy_configuration` (interest rate default 12%).

## 3. Scenario Suite

| Scenario | Description |
|---|---|
| **A** Current Condition | Validated intake values only |
| **B** Income Reduction | −5%, −10%, −15%, −20% |
| **C** Expense Increase | +5%, +10%, +15%, +20% |
| **D** Additional Obligation | Hypothetical extra EMI / medical / education / household (labelled) |
| **E** Combined Stress | e.g. income −10% & expenses +15%; presets admin-configurable |
| **F** Custom | Sliders + obligation + proposed-EMI adjustment, clamped to permitted ranges |

**Monthly projection** (up to 24 months): month *m* uses
`incomeₘ = income·(1+g_income)^(m−1)` and
`outflowₘ = (expenses+new obligation)·(1+g_expense)^(m−1) + EMIs`.
Reports month-wise balance, cumulative buffer, and the first stress month.
Explicitly labelled *assumption-based projection* — never a forecast.

## 4. Architecture & Isolation Guarantees

```
backend/services/financial_stress/
  calculations.py       pure deterministic arithmetic (no I/O)
  scenarios.py          scenario generation (config-driven steps)
  projections.py        12–24 month assumption projection
  stress_indicators.py  documented band classification
  explanations.py       template explanations (deterministic)
  schemas.py            pydantic validation + documented defaults
  service.py            orchestration, config versioning, RBAC, reports
backend/api/routes/stress.py   FastAPI routes (role-guarded)
backend/db/models.py           Application.monthly_expenses + StressScenarioConfig
```

**Isolation:** no code path writes hypothetical values into `applications`.
Scenario runs mutate nothing; report exports and officer assessments only write
`audit_logs` rows; configuration updates only append `stress_scenario_configs`
rows (previous versions retained; the newest is active).

**Access control:** applicant → own application via `applicant_user_id` match;
officer → any application; unauthenticated → 401; cross-tenant applicant → 403.
Config reads are transparent to authenticated users; writes are officer-only.
Report export logs `stress_report_exported` with user, role, and calc version.
Officer assessments log `stress_assessment_recorded` (advisory only).

**Frontend integration:** `FinancialStressSimulator.tsx`
(applicant "Understand Your Future Financial Position", live sliders, SVG
comparison + projection charts, downloadable HTML scenario report) and
`OfficerStressPanel.tsx` (compact advisory analysis inside the application
inspector, with optional assessment recording). No existing UI was removed;
the new applicant mode and the post-submission simulator entry are additive.

## 5. API Surface

| Method & Path | Access | Purpose |
|---|---|---|
| GET `/api/stress/applications/{id}/baseline` | owner/officer | Financial inputs + baseline metrics |
| GET `/api/stress/applications/{id}/scenarios` | owner/officer | Full suite A–E + worst case + default projection |
| POST `/api/stress/applications/{id}/custom` | owner/officer | Custom scenario (validated, clamped) |
| POST `/api/stress/applications/{id}/projection` | owner/officer | Assumption-based monthly projection |
| GET `/api/stress/applications/{id}/report` | owner/officer | Full JSON report (audit-logged) |
| POST `/api/stress/applications/{id}/assessment` | officer | Advisory assessment note (audit-logged) |
| GET/PUT `/api/stress/config`(+`/default`,`/history`) | read: authenticated · write: officer | Documented config & version history |

Validation: negative/absurd inputs rejected (`ge=0` bounds) or clamped to
admin-configured limits (`income_reduction_max`, `expense_increase_max`,
`additional_obligation_max`, `proposed_emi_max_multiplier`).

## 6. Experimental Evaluation Design

**Research question:** *"How can assumption-based financial stress simulation
improve the transparency and interpretability of credit affordability assessment?"*

### Experiments 1–4 (deterministic, fully reproducible — no human subjects)
Controlled test cases are hand-verified in
`backend/tests/test_financial_stress.py` (49 tests, all passing):

- **Experiment 1 — baseline vs scenario affordability:** FOIR-only baseline
  (only income+EMIs) vs scenario-informed view (adds expenses, buffer %, shocks).
  Metrics: FOIR change per shock, scenario coverage (12 predefined + custom).
- **Experiment 2 — income reduction impact:** remaining balance slope
  (−Δ1000 per −5% in the reference case) and indicator transition points.
- **Experiment 3 — expense inflation impact:** balance slope (+1700 per +5%);
  compared against income-side sensitivity.
- **Experiment 4 — combined shocks:** super-additive compression of buffer in
  combined scenarios vs single-axis shocks.
- **Experiment 6 — consistency/repeatability/sensitivity:** identical inputs
  produce identical outputs (repeatability); unit sensitivity of balance to each
  input verified against hand-computed arithmetic; EMI verified against standard
  loan tables (₹1,00,000 @ 12% / 36m ⇒ ₹8,884.88 for 12m; engine EMI formula).

**Measured example (reference case: income ₹50,000, EMIs ₹5,000, expenses
₹20,000, EMI ₹10,000):** baseline balance ₹15,000 (30% of income, FOIR 30%);
−20% income ⇒ ₹5,000 (REDUCED_BUFFER); +20% expenses ⇒ ₹11,000; combined
−10%/+15% ⇒ ₹7,000; custom −10%/+15%/+₹2,500 ⇒ ₹4,500 (ELEVATED_STRESS).

### Experiment 5 (user study — runs only if participants are available)
Within-subjects design: participants complete two affordability-understanding
tasks — (a) with the FOIR-only baseline card, (b) with the scenario simulator —
counterbalanced for order. Measures: task completion time, answer accuracy
against hand-verified ground truth, and comprehension self-report (single-item
7-point scale). **No participant data exists yet; none is fabricated.** If run,
raw data would be appended to `docs/` separately with the collection protocol.

### Explicit distinctions maintained throughout the UI
- "Under Assumptions" language on every stress indicator.
- HYPOTHETICAL badges on chips and report rows.
- Projection panel carries the literal disclaimer *"not a statistically trained
  forecast"*, consistent with `docs/LIMITATIONS.md` (selective-labels, cold-start).

## 7. Known Limitations

1. Monthly expensesdefault to 40% of income (documented assumption) when the
   applicant has not supplied them; the UI labels this everywhere and admin
   can change the ratio via config (versioned).
2. Proposed EMI uses the configured default rate (12% p.a.) because the intake
   does not capture a quoted rate; changeable via config without code changes.
3. The projection is linear-compounding of two user assumptions; it is not a
   calibrated forecasting model (by design, until validated history exists).
4. Stress thresholds are documented heuristics aligned to lending policy FOIR
   bands — not empirically calibrated probabilities.
5. Frontend visualisations are dependency-free SVG (no chart library) to keep
   the offline/local-first build self-contained.
